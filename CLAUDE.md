# gitbar

A native macOS menu bar app for git hosts — GitHub and GitLab (cloud and self-hosted) today, built so Bitbucket is one more module: pin repos, glance at PR/issue status, drill into details — all from a standard menu bar icon and popover.

## Current architecture (read this before touching UI or data flow)

**Menu bar icon + popover, not a notch.** An earlier direction tried to build this as a custom edge-docked "notch" window inspired by the app codenotch (https://github.com/vinzdg/codenotch). That was abandoned entirely — the custom AppKit window, hit-testing, and hover-trigger geometry proved too fragile to get right, and it never matched the product's own approved mockup anyway. **codenotch is no longer a reference for anything in this project.** Its code was fully removed (`Sources/Notch/`, `SideNotchShape`, `NotchMotion`, `NotchGeometry`, etc. — all deleted). Do not reintroduce notch-style UI, vendor codenotch code, or use it as a design reference unless the user explicitly asks again from scratch.

The real UI is `NSStatusItem` + `NSPopover` — stock AppKit, not hand-built. This is deliberate: show/close, outside-click dismissal, and positioning all come from the system instead of custom code.

### Screens (all SwiftUI, all in `Sources/Features/`)
1. **`RepoListPanel`** — pinned/favorited repos, one row each (icon, name, status label + meta text). Entry screen. The icon tile shows the provider's logo (`logo-<provider>` template asset) tinted by the **owning account's color** — `AccountColor` (Palette.swift; no green/orange/red, those mean status), picked per account in Settings → account → Appearance (`AccountColorPicker`, a System Settings-style swatch row — a `Picker` can't draw colored swatches), stored as `Account.color` (lenient decode; `nil` = automatic by list position, `Account.resolvedColor`). `LiveRepoStore.accountBadges` mirrors it as observed state via a `$accounts` subscription so an open popover repaints at once; hover tooltip names the account; the same color is a dot on the Settings sidebar row. Repo status lives only in the right-hand label's color.
2. **`RepoDetailView`** — one repo's open PRs/Issues, tabbed, paginated ("Load more"), scrollable within a fixed height. Under the header, a fixed-height **summary strip** (`RepoSummaryStrip`): description, then one line of chips — default-branch CI, latest release, stars, "N needs you" (PRs requesting your review) — from `ProviderClient.overview` (`RepoOverview` → `DisplayMapper.summary` → `LiveRepoStore.repoSummaries`, loaded with the repo-detail tier, best-effort). PR rows show their labels and, in the bottom row beside the status pill, when they were opened ("2h ago" — after the author it got truncated by long usernames); issue rows show labels, comment count and assignees, and open in the main window when clicked. Label chips (`LabelChip`/`LabelRow`, `Sources/DesignSystem/Chips.swift`) use the provider's own label color and `FirstFitRow` — one line, chips that don't fit are dropped (full list in the tooltip). Issues have a number search (`ProviderClient.issue`) and an "Assigned to me" checkbox (`gitbar.issueList.assignedToMe`, server-side `issues(repo:page:assignee:)` → `assignedIssues`), mirroring the PR tab's search + "Only mine".
3. **`PRDetailView`** — one PR's full detail: state, branches, description, reviewers, checks, comments. The composer's "Comment" posts a plain reply into the conversation thread (`ProviderClient.addComment` — GitHub issue comment, appended to the Comments section; disabled while the draft is empty), while Approve / Request changes submit a formal review (`ReviewDecision`, via `ProviderClient.submitReview`). If GitHub refuses a review because the user already has a pending draft review (started on the web), `GitHubClient.submitReview` submits that draft instead (`/reviews/{id}/events`), like "Finish your review". "Request changes" hides when the provider's `capabilities` say it has no such verdict. Also scrollable within a fixed height, header and composer pinned. The header shows the status pill, `#12` as a link to the web page, and the PR's URL with a copy button. Its window button opens the PR in the **main window** (below) with that PR selected; `PRDetailScreen` is the store-wired view the popover and the window share. There is no separate per-PR window any more (it was merged into the main window). The window follows the Settings window's look: `.fullSizeContentView` + `.unified` toolbar + `sceneBridgingOptions = [.toolbars, .title]`, so the PR title/repo sit in the titlebar and Copy Link / Open in Browser / Refresh are glass toolbar buttons beside the traffic lights (the loading state has a toolbar item too, or the titlebar falls back to the plain style). In the window (matching the mockup), the header carries status, number, "@author opened this …", title, head → base branches and the link; then the description, **Checks and Reviewers side by side** (stacked when the column is under 620pt, measured with `onGeometryChange`), and full-width Files changed and Comments, all scrolling in a centered readable column (max 980pt) and the composer uses stock bordered / borderedProminent buttons at `.large` control size, over a 13pt text-field-like box (accent border while focused; overlay scrollers via `OverlayScrollers`, since "Show scroll bars: Always" drew a track in the empty box; the placeholder sits at the editor's padding + NSTextView's 5pt line-fragment padding so it lines up with typed text; focus SwiftUI gives it on appear is cleared, nothing is focused until clicked). **Type sizes**: `DetailTypeScale` (Palette.swift) via the `detailType` environment — `.popover` keeps the compact sizes the popover was designed at, `.window` follows Apple's macOS scale (body/comments/check and reviewer names 13, file paths and diffs 12 mono, small actions/meta 11, chips 10 — never under the 10pt floor). `PRDetailView` sets it from `isWindowed`; the main window sets `.window` for everything inside it (list chips, issue screen); the issue screen and the diff (window-only) use `.window` directly; list rows use 13/11. New detail text takes its size from the scale, not a literal. The issue composer shares the PR window's `ComposerWell`, placeholder alignment, overlay scrollers and no-initial-focus rule. CI "running" uses `Palette.running` (a light/dark-tuned cyan-teal), never the system accent. Keyboard copy/paste/select-all/undo and ⌘W work because `AppDelegate` installs a (never shown) main menu with Edit/Window items — an accessory app without one routes no key equivalents to text views. **Dock presence**: the app is `.accessory` (menu bar only) while just the popover is in use, and `AppDelegate.updateDockPresence` switches it to `.regular` (Dock icon, ⌘-Tab, that main menu shown) whenever a titled window — Settings or the main window — is open or minimized, back to `.accessory` when the last closes. Clicking the Dock icon with everything minimized restores them (`applicationShouldHandleReopen`); the Window menu lists open windows.
4. **Main window** (`Sources/Features/MainWindowController.swift`: `MainWindowController`, one window, owned by `MenuViewModel` as `mainWindow`; `MainWindowState` = `MainSection` + selected PR/issue (`PRRef`, since lists mix repos) + selected inbox entry + expanded repos; closing keeps the state). The app is the main window; the popover is the quick glance; **Settings stays its own window** (Option A of the approved mockup — Apple's convention; putting settings in the sidebar was mocked as Option B and rejected). A three-column `NavigationSplitView`: sidebar = "For You" across every pinned repo (Review Requested = loaded PRs requesting you, Created by Me = each repo's `minePullRequests`, Assigned to Me = each repo's `assignedIssues`, Inbox = `NotificationStore` entries), then one section per account (`AccountBadge.title`/`position`/`webURL`, header dot in the account color; right-click: Refresh, Pin or Unpin Repos…, Account Settings… (`SettingsWindowController.showAccount` via `SettingsNavigator`), Open GitHub) with each repo a `DisclosureGroup` holding its Pull Requests / Issues; a bottom bar: **+** menu (Add Account…, Pin a Repository…) on the left, a gear on the right that opens Settings. Cross-repo rows carry a repo chip (account-colored dot + name) and are sorted by creation date (`RepoIssue.createdAt` exists for this); they show each repo's loaded first page (no cross-repo "Load more"). The list column is a native `List(selection:)` whose **first row is its search** (`searchRow`: `ListSearchField`, a wrapped large `NSSearchField` that takes focus only once clicked — it refuses `becomeFirstResponder` until then, since AppKit otherwise focuses a new window's first text field; not `.searchable`, which only goes in the toolbar). The search is part of the list, not the header (the owner's call). No hover fill on rows — Apple's own list apps (Mail, Notes) have none; one was added and removed at the owner's request. The titlebar title comes from the list column (`navigationTitle` on the detail column doesn't reach it): section name + repo path / repo count. A title over the detail column ("repo / #12") was tried and reverted: SwiftUI toolbar items can't be pinned over the detail (the toolbar is one strip over list + detail, leading items start over the list and are width-capped), and content drawn *under* the titlebar gets no clicks — a click there double-click-zoomed the window. Search matches title/author, plus repo in cross-repo lists; in a repo's list `12`/`#12`/`!12` falls back to the store's number search); the detail is `PRDetailScreen(isWindowed: true)`, `IssueDetailScreen` (`Sources/Features/IssueDetailView.swift`: description, labels/assignees, comments via `ProviderClient.issueComments`, composer via `addIssueComment`; store state `issueComments`/`beginIssueDetail`, keyed separately from PRs because GitLab's `#5` and `!5` coexist), or for an inbox thread the PR/issue when its repo is pinned (opening marks it read; the row stays listed while selected), else an "Open in Browser" page. **List selections go through `sticky(_:)`, which ignores `nil`**: a plain `List(selection:)` deselects when you click empty space or a search filters the selected row out, and that blanked the open PR. Switching to a repo's list drops a selected PR/issue from another repo. Opened from the popover's window buttons (repo header → its PRs, PR screen → that PR, issue rows → that issue), the popover gear menu's "Open gitbar", and Window → gitbar (⌘0, like Mail's Message Viewer); the app menu's Settings… (⌘,) opens Settings. Visiting a section loads what it draws from (`beginRepoDetail`/`beginMinePullRequests`/`beginAssignedIssues` per repo, all throttled); the background scheduler does the same for the visible section (`refreshTargets`, only while the window is open and not minimized) plus its selected PR/issue. A placeholder detail ("Select a…") still carries toolbar items (Open in Browser, Refresh) so the titlebar keeps the unified style. Sizing lives in `MainWindowMetrics`: columns sidebar 190–320 (230 preferred) / list 300–560 (380) / detail ≥460, `.balanced` split style so none collapses; the window opens like Mail — ~94% of a small screen, ~80%×85% of a large one, capped at what a readable 820pt detail column needs — and remembers its frame (`gitbar.mainWindow.v1` autosave name; bump it when the defaults change); the sidebar can be hidden with the toolbar toggle. **`.navigationSplitViewColumnWidth` must be the content column's last modifier** — with `.searchable` after it, SwiftUI silently ignored the width and the list opened ~200pt, narrower than the sidebar (verified by screenshot). Don't give the detail column an `ideal` width either. To check the layout, Debug builds accept `open gitbar.app --args -debugOpenMainWindow YES` (opens the main window on the first pinned repo with PRs at launch; `-debugOpenSettings YES` opens Settings; add `-debugOpenMainWindowPR YES` to select its first PR; delete the `NSWindow Frame gitbar.mainWindow.v1` default first to see the first-open size). It replaced the earlier one-window-per-repo design (and before that, one window per PR). Planned next: an Overview item per repo (from the approved mockup).

Navigation is a simple 3-level stack owned by `MenuViewModel` (`Sources/Features/MenuContentView.swift`): `selectedRepoID: RepoRef?` / `selectedPullRequestID: Int?` (plus `isCreatingPullRequest` for the create form), both nil = list. Push/pop uses spring animations + `.move(edge:)` transitions, not opacity crossfades — that distinction mattered a lot to the product owner (see Lessons below).

### Provider architecture (read before touching data flow)
Provider-neutral core + one self-contained module per git host. **Modules decide *what* to request and *how* to map it; the core decides *when* to fetch, how to throttle/cache, and how things look.** Nothing outside `Sources/Providers/<Name>/` may reference a provider's wire types or string states — the only kind-switch that reaches module code is `ProviderRegistry`.

```
Sources/Core/
  Provider/ProviderKind.swift     github|gitlab|bitbucket: display name, cloud host + cloud/self-hosted
                                  product names, token placeholder + help URL, terms (PR/MR, #/!), normalizeHost
  Provider/ProviderClient.swift   THE contract a module implements (actor, one per account)
  Provider/ProviderRegistry.swift isAvailable(kind) + makeClient(kind, host, token) — the only switch on kind
  Provider/ProviderError.swift    neutral errors; messages name the provider
  Networking/HTTPTransport.swift  shared HTTP: no-URLCache session, ETag/If-None-Match → 304 replay cache,
                                  JSON decode, status → ProviderError; provider rules via HTTPPolicy
  Domain/Domain.swift             neutral data: RepoRef, PRRef, AccountProfile, RemoteRepo, PullRequest, Issue,
                                  PullRequestState, PullRequestReviewStatus, PullRequestStatusSummary,
                                  CheckSummary, CheckRun/CheckRunStatus, Reviewer/ReviewState, Comment, ReviewDecision,
                                  CreatePullRequestDraft/FormData, PullRequestTemplate, Page, RateLimitStatus,
                                  ProviderCapabilities
  Display/DisplayModels.swift     what views render (RepoSnapshot, RepoPullRequest, RepoIssue, PRCheck, …)
  Display/DisplayMapper.swift     Domain → Display: every label, color, "time ago", status-ring rule — shared
Sources/Providers/GitHub/         GitHubClient (REST + GraphQL, github.com or GHES), GitHubDTOs (wire types),
                                  GitHubMapping (DTO → Domain, review/rollup states, HTTP conventions)
Sources/Providers/GitLab/         GitLabClient (REST v4 + one GraphQL query, gitlab.com or self-managed),
                                  GitLabDTOs (wire types), GitLabMapping (DTO → Domain, pipeline/job/todo states)
```

- **GitLab module** (`Sources/Providers/GitLab/`): API base `https://{host}/api/v4` (+ `/api/graphql`) for gitlab.com and self-managed alike (a host with a path, `example.com/gitlab`, works). Auth `Authorization: Bearer` (PATs on REST; the documented form for GraphQL). Projects are addressed by URL-encoded full path (`group%2Fsub%2Fproject`) — no numeric-id lookup. Pagination: `X-Next-Page`, else `Link`. Rate limit: `RateLimit-Remaining`/`-Reset`. Timestamps carry fractional seconds — `HTTPTransport.decodeDate` accepts both forms (plain `.iso8601` rejects GitLab's). Mapping choices: MR `iid` is the number; `statusSummaries` = one GraphQL query (`headPipeline.status`, `approved`, `approvedBy` — `approved` is true even with no rules, so "Approved" only once someone approved; very old schemas without the approval fields fall back to CI-only); `checks` = latest MR pipeline's jobs, **read from the pipeline's own `project_id`** (for an MR from a fork the pipeline runs in the fork — asking the MR's project 404s; verified on gitlab.com); `allow_failure` failures → neutral, manual → neutral; comments = notes minus system notes and inline `DiffNote`s; reviewers = `/reviewers` state (16+) merged with `/approvals`, both best-effort; files = `/diffs` (15.7+, falls back to `/changes`), line counts counted from the hunks; approve = `/approve` (+ the body as a note) — GitLab answers **401** when *you* may not approve, which `classifyError` turns into `validationFailed` by URL instead of "invalid token"; `supportsRequestChanges: false`; templates = `.gitlab/merge_request_templates` (project default description, then "Default", then by name); issues-disabled projects (403/404) read as no issues. Inbox = To-Do List (`/todos?state=pending`, mark done = `/todos/:id/mark_as_done`), `action_name` → `InboxItem.Reason`. Token access from `/personal_access_tokens/self` (15.5+; older → unknown): `read_api` reads everything incl. To-Dos, `api` needed for writes.
- **Repo overview** (`ProviderClient.overview`): GitHub = `/repos/{r}` + `/releases/latest` (404 = none) + default branch `check-runs` and legacy combined `status`, merged by `GitHubMapping.branchChecks`; GitLab = `/projects/:id` + `/releases?per_page=1` + `/pipelines?ref={default}&per_page=1`. All plain GETs (ETag 304s are free); only the repo call is required. Labels: GitHub REST/GraphQL `labels { name color }`; GitLab lists pass `with_labels_details=true` (`GitLabLabel` decodes a bare name or an object — single-item endpoints send names only, so those chips are neutral).
- **Diff link**: `PullRequest.diffURL` is set by the module (GitHub `{webURL}/files`, GitLab `{webURL}/diffs`) — the core never builds provider URLs.
- **Per-provider token copy**: `ProviderKind.tokenRequirements` (Add Account footer) and `notificationsTokenHint` (inbox empty state, Settings → Notifications footer — one hint per connected provider).

- **Identity**: `RepoRef { accountID, path }` everywhere a repo is keyed (store dictionaries, navigation, `RepoSnapshot.id`); per-PR state keys on `PRRef { repo, number }`. `path` is the provider's own full path, only unique within an account — so the same path under two accounts/providers is two repos (the old "owner/repo" collision is gone).
- **Accounts**: `Sources/Accounts/{Account,AccountStore,KeychainStore}.swift`. `Account { id, provider, host, login, name, avatarURL }`; `isCloud` = host is the provider's cloud host. Settings' Add Account asks Cloud vs Self-hosted explicitly (self-hosted requires a server; `normalizeHost` strips scheme/slash); the account screen shows a Cloud/Self-hosted badge. `addAccount(provider:host:token:)` validates via the registry's client (`validate()`); same provider+host+login re-stores the token instead of duplicating. **Migration**: records saved before providers existed have no `provider`/`host` and decode as `.github`/`github.com` (custom `init(from:)`) — don't remove that. Tokens: Keychain only, keyed by `account.id` (unchanged). GitHub host → API: `github.com` → `api.github.com`; anything else → `https://{host}/api/v3` and `/api/graphql` (GHES).
- **Favorites**: `Sources/Repos/FavoriteRepoStore.swift` — `[accountID: Set<path>]` (UserDefaults `gitbar.favoriteRepos.byAccount`), i.e. already a set of `RepoRef`s. `clearFavorites(for:)` on disconnect.
- **Live data**: `Sources/Repos/LiveRepoStore.swift` — neutral orchestration over `any ProviderClient` (one cached client per account, so rate-limit/ETag state stays per token):
  - Repo-list tier (cheap): `refresh()` fans out over every account's favorites — `recentPullRequests`/`recentIssues` (5 each), plus `reviewers` + `checks` only for your own PRs — into `DisplayMapper.snapshot`. An account with no token, no module, or low rate limit just contributes nothing.
  - Repo-detail tier: `pullRequests`/`issues(page:)`, 20/page, "Load more" appends (deduped). CI labels and the review verdict per row come from one batched `statusSummaries` call per page (GitHub: GraphQL `statusCheckRollup` + `reviewDecision`). The status pill (`DisplayMapper.statusChip`) is, in priority order: Merged / Closed (`PullRequest.state` — lists are open-only, but a PR opened from the inbox or refreshed after merging isn't), Draft, Review requested (from you), then Changes requested / Approved / Review required (provider verdict, else derived from loaded reviewers), else Open. **Running vs pending**: GitHub's rollup says PENDING for anything unfinished, including a commit status that waits on a person forever (a visual-review "changes must be accepted as baselines", a required check that never reports) after every Actions job, skipped ones included, has finished. So `statusSummaries` also reads `checkRunCountsByState` and only says `.running` while a check run is queued/in progress; otherwise `.pending` ("Checks pending", static, `Palette.attention`, not polled). The Checks list shows legacy commit statuses too (`/commits/{sha}/status`, description as tooltip), and a job held for a deployment approval (`waiting`) is `.pending`. Running CI is drawn with a `SpinningArc`, never static text (`ChecksStatusLabel`, `CheckRow`); while anything is running the PR screen polls `refreshChecks` every 20s (REST check-runs, ETag 304s are free) — popover only while it's shown — and re-reads the summary once when the last run finishes.
  - "Only mine" (checkbox by the PR search, `gitbar.prList.onlyMine`): a separate server-side list, `pullRequests(repo:page:author:)` — GitHub's REST PR list can't filter by author, so it's a GraphQL `search` (`repo:… is:pr is:open author:…`) returning full PR fields; the client maps page numbers to GraphQL cursors. Stored in `minePullRequests`; `updatePullRequest` updates both lists; opening one `adoptPullRequest`s it into `detailPullRequests` for the PR screen.
  - PR detail: checks/comments/reviewers lazily and independently on first open. `RepoPullRequest.source` keeps the domain `PullRequest` so follow-up calls (checks need its head SHA, reviewers its requested list) go back to the module.
  - Writes: `submitReview(decision:)`, `addComment`, `createPullRequest` (+ `loadCreatePullRequestForm`: branches, default branch, templates ordered with the provider's own prefill first). Provider rejections surface verbatim via `ProviderError.validationFailed`.
  - Rate limits: `rateLimitGuard` skips a batch under 50 remaining (`client.rateLimitStatus()`); `withRateLimitBackoff` does one wait-and-retry on `ProviderError.rateLimited` (the provider's `Retry-After`, capped at 2 min, else 60s).
- **Refresh cadence** (app-wide, every account on every provider; no request is ever unbounded or duplicated):
  - `RefreshScheduler` (`Sources/Repos/RefreshScheduler.swift`, owned by `StatusItemController`) polls every `gitbar.refreshInterval` seconds (General → "Refresh every", default 300, `-1` = manual only), skips ticks in Low Power Mode, refreshes ~5s after wake. Each tick: repo list, plus the visible repo/PR screen if the popover is open.
  - `LiveRepoStore.refresh(force:)` joins an in-flight run and skips within 60s of the last one (`minimumRefreshInterval`); only Retry buttons and PR creation pass `force: true`. Popover open calls it unforced.
  - `beginRepoDetail` / `beginPRDetail`: first visit loads; revisiting after 60s re-fetches. Repo detail merges a fresh page one over already-loaded "Load more" pages (`mergeFirstPage`), keeping each PR's lazily-loaded checks/comments/reviewers.
  - `HTTPTransport` sends every GET's cached `ETag` as `If-None-Match` and replays the cached body on `304` — verified on GitHub that 304s don't consume rate limit. Its session has no `URLCache`, so Foundation can't serve `max-age=60` responses from cache and hide the 304s. POSTs (GitHub's GraphQL: PR templates, per-page `statusCheckRollup`) aren't cacheable and always count.
- **Wording**: views take it from `ProviderKind` via `RepoSnapshot.provider` / `LiveRepoStore.provider(for:)` — "Pull Requests"/"Merge Requests", "New PR"/"New MR", `#12`/`!12`, "Refresh every", "Rate limit low". No provider name is hard-coded in UI copy.

### Notifications & token access
- **Token access** (`TokenAccess` on `Account.access`, persisted): `ProviderClient.tokenAccess()` — GitHub reads `X-OAuth-Scopes` from `GET /user` (classic tokens); `github_pat_…` = fine-grained (no scopes header, **can't read notifications at all**). Rules: notifications need `notifications` **or** `repo` (verified: a `repo`-only token reads them); PR writes need `repo`/`public_repo`. Checked on add, on demand (Settings → account → Token access → Re-check), once at launch for accounts missing it, and again whenever a notifications call comes back `.forbidden`.
- **403 handling**: GitHub 403 is `.rateLimited` only with `Retry-After` or `X-RateLimit-Remaining: 0`; otherwise `ProviderError.forbidden` (a permission problem — no retry/backoff).
- **`NotificationStore`** (`Sources/Notifications/`, owned by `SettingsWindowController`, shared with the popover via `MenuViewModel`): unread threads from every account with `capabilities.supportsNotifications` and a token that allows it. Own poll loop (`startPolling`, 60s with tolerance, never faster than the provider's `X-Poll-Interval`; unchanged inboxes are ETag 304s — free), plus a throttled refresh on popover open. Optimistic mark-read / mark-all-read.
- **Alerts** (`NotificationAlerter`, `UNUserNotificationCenter` delegate — created at launch so clicks on older alerts still route): only for threads new or updated since last alerted (`gitbar.notifications.seen`: thread → updatedAt); an account's **first** fetch records a silent baseline (`gitbar.notifications.baselined`) instead of alerting on the backlog. Per-reason toggles (`NotificationSettings`, default: review requested, mentions, assignments). Clicking an alert opens the popover to that item.
- **Opening an item** (`MenuViewModel.open`): marks read; a PR in a pinned repo opens in the app's PR screen (`LiveRepoStore.loadPullRequest` loads page one first, then the PR); anything else opens `webURL` in the browser.
- **UI**: bell + count in the popover top bar → `InboxView` (fixed size like the repo screen, grouped by repo); unread dot cut into the menu bar template icon (`StatusItemController.makeIcon`, re-armed via `withObservationTracking`); per-repo unread badge on repo rows; Settings → Notifications page.

### Adding a provider (e.g. GitLab)
1. Create `Sources/Providers/GitLab/` with its wire types, a mapping file (DTO → `Domain`, its state strings, `HTTPPolicy` rules: error classification, rate-limit headers, pagination), and `GitLabClient: ProviderClient` built on `HTTPTransport`. Map host → API base there (self-managed instances).
2. Set its `capabilities` honestly (e.g. `supportsRequestChanges: false` if it has no such verdict; `supportsNotifications` if it has an inbox API — GitLab's To-Do list, Bitbucket has none) and implement `tokenAccess()` — the UI adapts.
3. `ProviderRegistry`: return `true` from `isAvailable` and construct the client in `makeClient`.
4. Check `ProviderKind`'s wording/URLs for it (token help URL, placeholder, cloud/self-hosted names, terms) — they're already filled in for GitLab/Bitbucket.
5. The Settings sidebar, Add Account (cloud/self-hosted), account screen, favorites, popover, refresh and caching all pick it up with no further changes. Verify with `xcodebuild` + a real account.

- **Rendering PR bodies/comments/reviews natively**: `Sources/DesignSystem/MarkdownText.swift` (`RenderedBodyText`). An earlier version rendered the provider's server-rendered HTML (GitHub's `body_html`) through AppKit's legacy WebKit-based HTML importer — that was abandoned: it drops/mangles checkboxes and images and gives no real control over code-block/blockquote layout. The current renderer parses the provider's **raw Markdown** (`PullRequest.body`/`Comment.body`/`Reviewer.body`) directly with [`swift-markdown`](https://github.com/apple/swift-markdown) (`import Markdown`, SPM — pure Swift + a small C `cmark-gfm` target, no WebKit, licensed Apache-2.0, noted in NOTICE.md) into a `[MarkdownBlock]` tree, then renders every block type as its own native SwiftUI view: paragraphs/headings through `RichText` (below), fenced code blocks in a scrollable monospaced box (`CodeBlockView`), blockquotes with a drawn left accent bar (`BlockQuoteView`), ordered/unordered/task lists recursively with real checkboxes (`MarkdownListView`), tables via `TableGridView` (unchanged — fed AST cells instead of `NSTextTableBlock` parsing), and images through `MarkdownImageCache` (one fetch per URL per session; `version` bumps on each finished load so bodies containing `![` re-render). A paragraph made only of images (screenshots, badge rows, `[![alt](img)](href)`) becomes picture blocks (`ImageBlockView`) drawn at native size, only ever shrunk — not `AsyncImage` + `.scaledToFit()`, which upscales small badges into a blur. An image mixed with text (an icon before a label, an image inside a heading) is an inline `NSTextAttachment`, text-height if icon-sized. Plain flowed text still renders through a custom `NSTextView` (`RichText`/`LinkCursorTextView`) rather than SwiftUI's `Text`, specifically so a link gets its own pointing-hand cursor — decided per event in `LinkCursorTextView.mouseMoved`/`cursorUpdate` (own `.activeAlways` tracking area); cursor rects alone lose to `NSTextView` re-setting the I-beam on every move. **`RichText` measures height on a throwaway TextKit 1 stack, and the live view is built explicitly on TextKit 1 too** — measuring by resizing the live view's container to each width SwiftUI probed left it wrapping at the wrong width, so text drew taller than measured and overlapped the next block. Parsed `[MarkdownBlock]` trees are memoized (parsing is fast — no WebKit spin-up — but `body` still runs on every popover redraw), and `RichText.updateNSView` only resets text that actually changed.
- **Settings window**: `Sources/Settings/{SettingsWindowController,SettingsView}.swift` — real `NSWindow`, singleton, `NavigationSplitView` sidebar+detail (System Settings-style, not tabs). Sidebar: General, Notifications, then one row per `ProviderKind` under "Accounts" — an available provider is a disclosure row with its accounts (each → `AccountDetailView`, repo/favorites picker via `AccountStore.repositories(for:)`) plus "Add Account"; an unavailable one is a "Soon" row (`ComingSoonView`). Generated from `ProviderKind.allCases`, so a new module appears automatically. Reached via the popover's gear menu → "Settings…", the app menu's Settings… (⌘,), or the main window's account menus (`SettingsNavigator` switches the page). The window owns its size (`hosting.sizingOptions = []` — the default options blanked the whole window when switching detail screens) and bridges SwiftUI toolbars/titles into a unified titlebar (`sceneBridgingOptions`). Every detail screen follows **Settings screen conventions** below.
- **General settings**: `Sources/Settings/GeneralSettingsView.swift` — sidebar's first row. Appearance (`AppearanceMode`: System/Light/Dark → `NSApp.appearance`, stored in `UserDefaults` `gitbar.appearance`, applied at launch in `AppDelegate`; the popover has no forced appearance and follows it), Open at login (`SMAppService.mainApp`, status read live since the user can change it in System Settings), Updates, and the current version (`MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` in project.yml).
- **App + menu bar icons**: `AppIcon.appiconset` is generated by `swift scripts/make-icons.swift` (drawn in code, all 10 PNG sizes — edit the script, not the PNGs). The menu bar icon is `MenuBarIcon.imageset`, a hand-written 18×18 template SVG. The mark is a bar with a panel dropping from it (the app's own popover shape) — deliberately *not* git imagery, which the user rejected as misleading, set on the status item with `isTemplate = true` and reused in the popover header.
- **Provider logos**: real GitHub/GitLab/Bitbucket marks as template SVGs in `Sources/Resources/Assets.xcassets` (`logo-<rawValue>`, Simple Icons, CC0 — noted in NOTICE.md), drawn via `ProviderLogoView(provider:)` in `SettingsView.swift`. SF Symbols has no brand logos; don't swap these back to generic symbols.
- **Updates**: Sparkle 2 (SwiftPM), wrapped by `Sources/Settings/AppUpdater.swift`, owned by `SettingsWindowController`. Feed: `SUFeedURL` = `https://github.com/NavaneethVijay/gitbar/releases/latest/download/appcast.xml` (each GitHub release carries the zip + `appcast.xml`). `SUPublicEDKey` is written by `make update-keys` (private key stays in the login Keychain). Sandboxed install path: `SUEnableInstallerLauncherService` + the `-spks`/`-spki` mach-lookup entitlements. `CFBundleVersion` == marketing version (`x.y.z`) — Sparkle compares it against the appcast, so never go back to an integer build counter (an integer sorts above `0.x.y`).
- **Installing from source is the only distribution — no `.dmg`/prebuilt downloads, by the owner's decision.** Don't publish releases or point users at downloads; README's Install section is the user-facing guide (keep it step-by-step for a fresh Mac). Installing from source (`make install` → `scripts/install.sh`): no Developer ID means downloaded builds are quarantined and blocked by Gatekeeper — on the author's machine "Open Anyway" even left `/Applications/gitbar.app` held at `_dyld_start` (identical binary ran fine from any other path) until a restart cleared it. Local builds are never quarantined. `install.sh` sets `SUEnableAutomaticChecks`/`SUAutomaticallyUpdate` to false in the installed Info.plist (an update Sparkle downloads would be quarantined too); updating is `git pull && make install`. Build + signing for both install and release live in `scripts/build-app.sh`.
- **Releasing** (dormant tooling — not used, see above; kept only in case that decision changes; `scripts/release.sh`, via `make release VERSION=x.y.z` / `make release-dry`): Release build, universal (`-destination generic/platform=macOS`), ad-hoc signed (`SIGN_IDENTITY=-` default; no Developer ID yet), Sparkle's XPC helpers re-signed inside-out, zip, `generate_appcast` (sees only the zip), then a DMG (app + `/Applications` symlink, built after the appcast) for first installs, `gh release create --repo NavaneethVijay/gitbar` with DMG + zip + appcast, then bumps the versions in project.yml. **Ad-hoc ⇒ hardened runtime OFF** — with it on, library validation refuses to load the ad-hoc `Sparkle.framework` ("different Team IDs") and the app dies at launch; verified. Turn it back on only with a real Developer ID (and add notarization then). `CODE_SIGN_INJECT_BASE_ENTITLEMENTS=NO` keeps `get-task-allow` out of release builds.

### Settings screen conventions (every detail screen — follow these for any new page)
**Target look: current macOS (26) native — the unified titlebar with glass toolbar buttons, like System Settings.** `GeneralSettingsView` is the reference screen; match it. When screens drift apart, fix it by bringing the odd one up to this pattern — never by stripping toolbar items or moving actions inline (that was tried and read as the old, flat macOS look).

- **Wrapper**: one `Form { … }.formStyle(.grouped)` + `.navigationTitle(<sidebar row name>)`. No custom full-screen layouts (`ContentUnavailableView`, hand-built hero headers, bare `VStack`s) — the "Soon" provider page used `ContentUnavailableView` and looked like a different app.
- **Sections**: every `Section` has a `header: { Text("Title Case") }` — including the first one (a header-less first section starts higher than every other screen). Add a `footer:` explaining the section in a sentence, `.foregroundStyle(.secondary)`. One topic per section; split long toggle lists into their own titled section (Notifications: Inbox / Alerts / Alert Me About / Accounts).
- **Rows**: stock controls only — `Toggle`, `Picker` (`.segmented` for 2–3 short options, default menu otherwise), `LabeledContent("Label", value:)` for read-only facts, `TextField`/`SecureField` with a `prompt:`. Status as `Label(text, systemImage:)` tinted green/orange/red (see `AccessRow`, `accountStatus`). Warnings inside a section: orange `Label` + trailing `Button` (see "Needs approval…" / "Alerts are turned off…").
- **Actions go in the toolbar**, as `ToolbarItem { Button("Name", systemImage: "…") { … }.help("…") }` — icon buttons, glass-styled by the system. Search is `.searchable(text:, placement: .toolbar, prompt:)`. A primary submit uses `ToolbarItem(placement: .confirmationAction)` + `.keyboardShortcut(.defaultAction)` (Add Account → Connect). Don't put buttons in section headers or text-link buttons in rows as a substitute.
- **Every detail screen must have at least one toolbar item.** With none, SwiftUI drops the window's toolbar entirely and the traffic lights jump out of the sidebar into a plain title bar — the screen looks broken next to the others. Current items: General → Check for Updates, Notifications → System Settings, account → search + Refresh, Add Account → Connect, "Soon" provider → Open in browser. A new page with no natural action still needs one relevant button.
- **Every manual action confirms itself with a toast** (the owner asked for feedback "always"): Refresh in the PR/issue screens awaits the forced fetch (`refreshPRDetail`, `refreshIssueDetail`) and then says "… is up to date"; the main window's toolbar Refresh and the account/repo right-click Refresh go through `MainWindowState.refresh` — "Refreshing …" then "… is up to date" (or the rate-limit warning) — using `LiveRepoStore.refreshRepoDetail`, which skips the 60s throttle (`beginRepoDetail` is throttled, so a Refresh button calling it could silently do nothing). Copying a link (toolbar Copy Link, the header link's copy button, right-click Copy Link) toasts "Link copied" — the detail screen passes its toast down as the `onLinkCopied` environment action. New actions follow the same rule.
- **Transient feedback**: a bottom `floatingCapsule()` toast with a spring `.move(edge: .bottom)` transition (see `AccountDetailView.showToast`), not alerts/sheets for success.
- **Live system state** (login item, notification permission) is read from the system on appear and re-read on `NSWindow.didBecomeKeyNotification`, never cached in a stored flag — the user can change it in System Settings while the window is away.
- **Adding a page**: add a case to `SettingsView.Selection`, a sidebar row (`Label("Name", systemImage:)` + `.tag`), a branch in `detail`, and a `…SettingsView` struct following the rules above. Verify by switching between it and General — title bar, first-section position and control styles should not shift.

### Known simplifications (deliberate, not bugs)
- No merge-conflict detection in the state computation (would need the single-PR-detail endpoint, an extra call per PR — skipped to bound request volume).
- Issues have a detail screen only in the main window (popover issue rows open it there). No closing/editing issues, and lists are open items only (no Closed/Draft filter).
- No reviewer *request* picker — the Reviewers section is stats/status only (who's approved / requested changes / still pending). Requesting new reviewers would need a repo-collaborators fetch + picker UI, deliberately out of scope for this pass.
- Rate-limit backoff is "one wait-and-retry," not a full exponential scheduler — proportionate to a menu bar app's modest request volume.
- Bitbucket has no module yet — the architecture is in place (see "Adding a provider"), but `ProviderRegistry.isAvailable` is false for it, so it shows as "Soon".
- GitLab: no "Request changes" from the app (hidden via `capabilities`); reviews carry no separate body (the text becomes a note); child-pipeline / bridge jobs aren't listed under Checks (only the MR pipeline's own jobs). Avatars on a **private self-managed instance** can't load: GitLab serves `/uploads/…` only to browser sessions — it refuses access tokens there (Bearer and `PRIVATE-TOKEN` both 401, verified on 19.5.3) and no API route returns avatar bytes — so Settings' `Avatar` falls back to initials. Don't re-add authenticated avatar fetching; it can't work.
- Tokens are PATs only — no OAuth flow for any provider.
- The repo-list status ring's "busy" signal still calls `checks` per own PR (REST, ETag-cacheable) rather than the batched `statusSummaries` (GitHub GraphQL, never cacheable) — deliberately, so background polls of quiet repos stay free.
- Markdown rendering (`RenderedBodyText`) has two disclosed gaps: no syntax highlighting inside fenced code blocks (monospaced + boxed only), and no code-block/table cell alignment beyond plain left-alignment. Rare raw HTML in a body (outside GFM's own checkbox/image/table syntax) degrades to tag-stripped plain text rather than a real sub-render.
- **Inline diffs (PR window only)**: each file's unified-diff `patch` rides along on the same `files` request (GitHub omits it for binary/too-large files → a "View on web" note) — no extra calls. `Sources/Core/Diff/UnifiedDiff.swift` parses it (provider-neutral; line numbers from hunk headers) only when a file is expanded, off the main thread; `Sources/Features/DiffView.swift` draws it as lazy monospaced rows, wrapped (no horizontal scroll — it would defeat laziness), 300 lines per "Show more" batch. Generated/vendored files (`isLikelyGenerated`: lock files, `.min.js`, `dist/`, snapshots…) and changes over 500 lines start behind "Show diff". Each file is a direct child of the window's `LazyVStack`, so off-screen files aren't built. No syntax or intra-line word highlighting, by choice. The popover keeps the one-line-per-file list.
- A PR's "Files changed" section (`ProviderClient.files`) fetches a single page (100 files, matching the same bounded-request-volume choice as `comments`) — a PR with more changed files than that shows only the first 100.

### Rendering & performance rules (from a GPU/flicker pass — keep these)
- **Stable popover size.** The popover window follows its content (`sizingOptions = [.preferredContentSize]`), and window resizes are expensive and flicker-prone. So the repo / PR / create screens have fixed heights (`RepoDetailMetrics.height`, `PRDetailMetrics.height`) and scroll inside; the window only resizes when navigating. Don't go back to `maxHeight` caps.
- **No no-op writes.** `LiveRepoStore` is `@Observable` (per-property invalidation); its bookkeeping is `@ObservationIgnored`. Every UI-visible write goes through `assign(_:_:)`, which skips equal values — most background refreshes are 304s that change nothing. Display models must stay `Equatable` with content-derived ids (`PRCheck.id`, `PRComment.id` — never `UUID()`), or equality never holds.
- **Translucency is optional.** General → "Solid background" (`gitbar.solidBackground`), forced on by the system's Reduce Transparency; read via `SolidBackgroundReader` (popover surface + `floatingCapsule` toasts).
- **Lazy lists** (`LazyVStack`) for the repo PR/issue list and the PR screen's sections/comments.
- **Text:** `RenderedBodyText` parses synchronously and caches the parsed blocks per body; `RichText` caches its measured height per width. `updateNSView` only resets changed text.
- **Cursor:** `.pointerStyle(.link)` via `hoverHighlight` — no `NSCursor.push/pop` (leaks when a hovered row disappears).
- **Timers:** the refresh sleep carries a tolerance so macOS can coalesce wakeups.

## Working conventions for this project

- **Every change gets verified with a real `xcodebuild`, not trusted from a report.** This came up constantly — subagent self-reports of "build succeeded" were independently re-verified every time before being passed on to the user. Keep doing this.
- `make run` kills the running instance, rebuilds, relaunches. Standard verification loop: edit → `make build` → `make run` → confirm PID alive.
- SourceKit "cannot find type in scope" diagnostics that appear mid-edit are almost always stale-index noise, not real errors — `xcodebuild` is the source of truth, not the live diagnostics.
- Fork (background agent) for heavy, multi-file, self-contained work (new subsystems: auth, data layer, bulk vendoring). Do sequential UI/polish fixes directly in the main thread — the user explicitly pushed back on forking for small iterative changes ("why do you need to fork... you are just idle").
- Match the approved mockup literally, down to exact meta text per row, not a paraphrased/regenerated version. Several rounds of rework happened because generated text ("N open PRs" everywhere) silently diverged from what the mockup actually specified per-row.
- Real interaction affordances matter: hover highlight must fill the actual clickable area (own the row's height inside the row view, not applied externally — externally-applied height left the highlight smaller than the click target), and a pointing-hand cursor belongs only on rows that actually do something on click (not decorative ones).
- Any list that can grow unboundedly (pagination, long comment threads) needs a capped, scrollable height — a popover sizes itself to its SwiftUI content, so unbounded content means an unbounded popover, up to filling the screen.
- Content transitions should feel physical (spring-driven move/scale), not a flat opacity crossfade — this was explicitly called out as feeling "mechanical" and fixed by using `.move(edge:)` + spring instead of `.opacity` alone.

## Build

```
make install                    # Release build from source → /Applications, opens it (the supported install path)
make run                        # xcodegen + Debug build (unsigned) + relaunch
make build                      # build only
make update-keys                # one-time: Sparkle EdDSA key → project.yml
make release-dry VERSION=x.y.z  # Release build/sign/appcast into build/release, publishes nothing
make release VERSION=x.y.z      # same + GitHub release
```

Everything builds into `build/DerivedData.noindex` (so Sparkle's CLI tools are at `build/DerivedData.noindex/SourcePackages/artifacts/sparkle/Sparkle/bin`). Debug builds are unsigned and therefore **not sandboxed** — sandbox behavior only shows up in `make release-dry` builds; test there before shipping anything that touches files, network or Keychain.

`NSSupportsAutomaticGraphicsSwitching: true` (project.yml info properties — the `INFOPLIST_KEY_` form doesn't work for it) keeps the app off the discrete GPU on dual-GPU Macs; forced switches glitched the whole screen on the author's 2019 16" MacBook Pro (Intel UHD 630 + AMD 5500M, macOS 26).

Bundle id `com.navaneeth.gitbar` (renamed from `com.navaneeth.gitsidebar` before the first release — no data migration, by decision). Author: NavaneethVijay (https://github.com/NavaneethVijay). macOS 15+ deployment target. Two SwiftPM dependencies, declared in project.yml: Sparkle (auto-updates) and swift-markdown (Markdown parsing).
